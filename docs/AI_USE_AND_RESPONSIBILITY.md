# AI 사용과 책임

## 사용 범위

수집 스크립트와 정제 로직 구현에 코딩 보조 도구를 사용했습니다. 문서 작성에도 사용했습니다.

## 사람이 판단한 것

| 항목 | 판단 내용 |
|---|---|
| 문제 정의 | 수집 로그가 전부 성공인데 데이터가 비는 현상을 문제로 규정 |
| 상태 모델 | 결과를 성공, 데이터 없음, 오류 셋으로 나눌 것 |
| 품질 지표 | 키 중복과 키 충돌을 분리해 기록할 것 |
| 정제 규칙 | 완전 동일 행만 제거하고 값이 다른 중복은 남길 것 |
| 타입 정책 | 코드 컬럼을 문자열로 유지할 것 |
| 이상치 처리 | 세기만 하고 버리지 않을 것 |
| 수행 위치 | 규칙 확정 전까지 로컬에서 반복할 것 |
| 실패 기록 | 중단된 실행을 지우지 않고 남길 것 |
| 비용 접근 | 총액이 아니라 항목 구성부터 볼 것 |
| 무엇을 주장하지 않을지 | 검증되지 않은 수치를 문서에서 제외할 것 |

## 도구가 알려주지 않은 것

**명세와 실제 응답의 필드명이 다르다는 것.** 파서는 정상 동작했고 예외도 없었습니다. 값 분포를 직접 확인해서 찾았습니다.

**기관 안내가 실제와 다르다는 것.** 안내받은 시작 시점보다 앞선 요청에 응답이 오는 것을 보고 확인했습니다.

**비용의 원인이 저장이 아니라 요청이라는 것.** 저장소 비용이니 저장을 줄이면 된다는 것이 자연스러운 추론입니다. 항목별로 나눠 본 뒤에야 알았습니다.

세 경우 모두 **결과가 이상하다고 느껴서 확인한 것**이지 도구가 지적한 것이 아닙니다.

## 도구를 쓰고도 놓친 것

앞의 세 가지와 성격이 다른 항목이라 따로 적습니다.

수집 러너 3종의 서비스키 마스킹이 서로 다르게 잘못돼 있었습니다. 한 러너는 함수가 아예 없었고, 다른 러너는 정규식 이스케이프가 잘못돼 마스킹한 것처럼 보이면서 키 뒷부분을 남겼으며, 나머지 하나는 함수 이름과 동작이 달랐습니다. 상세는 [PROVENANCE.md](./PROVENANCE.md)에 있습니다.

세 러너를 각각 다른 시점에 작성하면서 같은 함수를 복사해 손봤는데, 그 과정에서 생긴 차이를 잡지 못했습니다. 당시 코드 리뷰 노트([code_review_notes.md](./code_review_notes.md))도 이 부분을 짚지 않았습니다.

도구는 이것을 지적하지 않았고, 저도 눈으로 읽고 통과시켰습니다. 2026년 공개를 준비하며 같은 코드를 다시 읽고 나서야 찾았습니다.

여기서 정한 규칙은 하나입니다. **보안 유틸리티는 읽어서 통과시키지 않고 실행해서 확인합니다.** 정규식처럼 조용히 실패하는 것은 특히 그렇습니다. 그래서 이 저장소에는 마스킹 자체를 검증하는 테스트가 들어 있습니다.

## 경계

- 프롬프트별 제안과 채택과 거절을 완전하게 연결한 기록은 없습니다
- 도구를 사용하지 않고 직접 작성한 비율을 주장하지 않습니다
- 도구 사용 여부와 무관하게 결과에 대한 책임은 작성자에게 있습니다
- 마스킹 결함을 찾아 고친 것도 이 원칙의 결과이지 도구의 성과가 아닙니다
