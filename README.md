# 농업기상 수집 파이프라인

공공 API 3종에서 받은 데이터가 수집 로그상 전부 "성공"인데도 적재 결과에 구간이 비어 있던 문제를 다룹니다. 응답 성공과 의미상 정상을 분리해 판정하고, 실행마다 품질 지표를 남겨 중복 제거가 안전했는지를 숫자 하나로 확인할 수 있게 만들었습니다.

> 5인 교육 팀 프로젝트에서 제가 단독으로 담당한 농업기상 branch를 공개 가능한 범위로 재구성했습니다. 수집기와 정제기는 당시 작성한 코드 그대로이며, **로컬 백필 레퍼런스 구현이지 AWS 운영 실적이 아닙니다.** 팀의 다른 축, 원본 자료, 팀원 정보, 계정 식별자, 수집한 원시 데이터는 포함하지 않습니다.
>
> 앞선 과제에서 3계층 환경에 관측 스택을 직접 붙여 본 경험이 여기서 실행 단위 품질 메타를 설계한 배경입니다. 그쪽은 [aws-3tier-observability](https://github.com/procloudkim/aws-3tier-observability)에 있습니다.

## 3분 요약

| 질문 | 답변 |
|---|---|
| 어떤 문제인가 | 기상청과 농촌진흥청 공공 API 3종을 10년 이상 구간으로 수집하는데, 수집 로그는 전부 성공인데 적재 결과에 구간이 비어 있었습니다 |
| 왜 로그를 믿을 수 없었나 | 세 가지가 어긋났습니다. 기관이 안내한 제공 시작 시점이 실제와 달랐고, 명세의 필드명과 실제 응답의 필드명이 달랐으며, 서버가 빈 결과를 200으로 돌려주는 경우가 있었습니다 |
| 무엇을 바꿨나 | 결과를 성공, 데이터 없음, 오류 셋으로 나눠 판정하고 오류만 재시도하게 했습니다. 파서는 명세가 아니라 실제 응답을 기준으로 맞췄습니다 |
| 손실이 없다는 것을 어떻게 보이나 | 실행마다 품질 메타를 남깁니다. 키 중복과 키 충돌을 분리해 기록하므로 중복 제거로 지운 행이 안전했는지 숫자로 판정할 수 있습니다 |
| 실제 결과는 무엇인가 | 세 원천 모두 키 충돌 0으로 정리됐습니다. 가장 큰 원천은 입력 3,103,904행에서 완전 동일 행 977,389건을 제거해 2,126,515행이 됐습니다 |
| 실패한 실행은 어떻게 다뤘나 | 지우지 않고 실행 ID와 중단 사유를 리포트에 남겼습니다. 성공만 남기면 같은 문제를 다시 만납니다 |
| 비용 문제는 어떻게 접근했나 | 청구 총액이 아니라 항목 구성을 먼저 봤습니다. 대부분이 저장 비용이 아니라 요청 비용이었고, 흔히 떠올리는 저장 최적화는 해법이 아니었습니다 |
| 공개하면서 무엇을 고쳤나 | 자기 코드를 다시 읽고 마스킹 결함 3건을 찾아 고쳤습니다. 아래 킬링 파트 두 번째 항목입니다 |
| 본인의 역할은 무엇인가 | 5인 팀에서 농업기상 축의 수집부터 대시보드까지를 단독으로 담당했습니다. 팀의 다른 축은 다른 구성원이 소유했습니다 |
| 무엇을 입증하지 않았나 | 프로덕션 운영, 실사용자, 트래픽, 성능 우위, 비용 절감액, 팀 전체 플랫폼의 소유는 입증하지 않습니다 |

## 킬링 파트

### 1. 키 중복과 키 충돌을 나눈 것

품질 메타에서 이 둘을 분리한 것이 이 파이프라인의 중심입니다.

키가 겹쳐도 나머지 값이 완전히 같으면 안전하게 지울 수 있습니다. 값이 다르면 어느 쪽이 맞는지 판단이 필요하고, 그냥 지우면 데이터를 잃습니다. 둘을 뭉뚱그리면 **조용히** 잃습니다. 로그에는 아무 표시도 남지 않습니다.

두 값의 관계는 이렇게 성립합니다.

```
키 충돌 = 키 중복 − 행 중복
```

키 충돌이 0이면 지운 행이 전부 완전 동일 행이었다는 뜻입니다. 300만 행에서 97만 행을 지웠는데 손실이 없었다는 것을 숫자 하나로 보일 수 있습니다.

이 불변식은 [`tests/test_dq_invariant.py`](./tests/test_dq_invariant.py)에서 검증합니다. 원본 데이터 없이도 클론해서 바로 돌려볼 수 있습니다.

### 2. 공개 준비 중에 자기 코드에서 찾은 마스킹 결함 3건

이 저장소를 만들면서 수집기 3종을 다시 읽었습니다. 서비스키 마스킹이 세 곳 모두 다르게 잘못돼 있었습니다.

| 러너 | 상태 | 실제 결과 |
|---|---|---|
| `rda_basic_daily` | 마스킹 함수가 **없음** | 서비스키가 붙은 URL이 예외 메시지에 실려 manifest와 로그에 그대로 기록됨 |
| `rda_crop_daily` | 함수는 있으나 정규식 이스케이프 오류 | 치환 결과가 리터럴 `\1***`가 되고 키 뒷부분이 남음. **마스킹한 것처럼 보이면서 유출** |
| `kma_crop_detail` | `sanitize_params`가 인자를 그대로 반환 | 이 러너는 키를 URL에 미리 붙여 전달해 유출 경로는 없었으나, 이름이 하는 일과 코드가 달랐음 |

셋 다 고치고 [`tests/test_redaction.py`](./tests/test_redaction.py)로 검증을 붙였습니다.

두 번째가 가장 무섭습니다. 마스킹이 없는 코드는 없다는 걸 알기라도 하지만, **잘못된 마스킹은 있다고 믿게 만듭니다.** 당시에는 세 러너를 각각 다른 시점에 쓰면서 같은 함수를 복사하고 손봤는데, 복사 과정에서 이스케이프가 한 단계 더 들어간 것을 잡지 못했습니다.

여기서 얻은 규칙은 하나입니다. **보안 유틸리티는 눈으로 읽어서 통과시키지 않고 반드시 실행해서 확인합니다.** 정규식은 특히 그렇습니다.

## 왜 로그를 믿지 않게 됐나

수집 스크립트는 요청을 보내고 응답 코드를 확인한 뒤 결과를 기록합니다. 200이면 성공입니다. 이 구조에서 로그는 전부 성공이었습니다.

그런데 적재 결과를 보면 특정 구간이 비어 있었습니다. 원인은 세 갈래였습니다.

**첫째, 기관 안내와 실제 제공 범위가 달랐습니다.** 담당자에게 안내받은 시작 시점부터 요청을 넣었는데 그보다 앞선 기간에도 응답이 왔습니다. 연도를 하나씩 내려가며 확인한 결과 안내보다 이전부터 데이터가 제공되고 있었습니다. 안내를 그대로 믿었다면 수집 범위 자체가 잘못 잡혔을 것입니다.

**둘째, 명세의 필드명과 실제 응답의 필드명이 달랐습니다.** 특보 관련 컬럼을 명세 기준으로 파싱했더니 값이 전부 비었습니다. 응답 원문을 열어보니 필드명이 문서와 달랐습니다. 파서는 정상 동작했고 예외도 발생하지 않았습니다. 존재하지 않는 키를 조회하면 빈 값이 나올 뿐입니다.

**셋째, 빈 결과가 200으로 왔습니다.** 서버가 요청을 정상 처리하고도 결과가 없는 경우가 있었습니다. HTTP 계층에서는 성공이고 의미 계층에서는 데이터가 없습니다. 둘을 같게 처리하면 구멍이 조용히 남습니다.

> 프로젝트 회고에 이렇게 적었습니다.
> **"수집이 성공했다는 로그만 믿지 않고, 항상 먼저 확인하는 습관을 시작하겠습니다."**

## 상태를 셋으로 나눈 이유

수집 결과를 성공과 실패 둘로 나누면 다시 돌릴 때 판단할 수 없습니다.

| 상태 | 의미 | 재실행 정책 |
|---|---|---|
| 성공 | 응답이 왔고 데이터가 있음 | 건너뜀 |
| 데이터 없음 | 응답이 정상이고 해당 구간에 데이터가 원래 없음 | 건너뜀 |
| 오류 | 요청 실패 또는 판정 불가 | 재시도 |

데이터가 원래 없는 구간을 계속 재시도하면 시간과 호출 한도를 소모합니다. 반대로 실패를 성공으로 처리하면 구멍이 남습니다. 셋으로 나누면 재실행 범위가 자동으로 좁혀집니다.

수집 단위마다 이 판정을 manifest에 기록하고, 다음 실행은 `--resume`으로 기록을 읽어 남은 것만 처리합니다.

## 만든 것

```
공공 API 3종
  │  코드북 조사, 명세 대조, 장기 backfill
  ▼
RAW (XML 원문 보존)
  │  파싱, lineage 컬럼 부착
  ▼
BRONZE (CSV)
  │  키 정규화, 결측 정규화, 중복 판정, 날짜 파싱, 이상치 계수
  ▼
SILVER (Parquet, 관측일자 파티션)  ──▶  품질 메타 (실행 단위)
  │  표준화, 코드북 매칭
  ▼
GOLD (테이블과 뷰)
  │
  ▼
기상특보 모니터링 대시보드
```

당시 환경은 AWS Lambda, S3, Glue, Step Functions, EventBridge, Athena, QuickSight였습니다. 이 저장소에 담긴 것은 그중 **수집과 Bronze에서 Silver까지의 로컬 레퍼런스 구현**입니다.

## 품질을 숫자로 만드는 방법

정제 단계마다 다음을 실행 단위로 기록합니다.

| 필드 | 무엇을 판정하는가 |
|---|---|
| 입력 행수, 출력 행수 | 전체 변화량 |
| 키 결측 | 식별자가 없어 버려진 행 |
| 키 중복 | 같은 키가 여러 번 등장한 횟수 |
| 행 중복 | 키와 나머지 값이 모두 같은 행의 수 |
| 키 충돌 | 키는 같은데 값이 다른 경우의 수 |
| 날짜 파싱 실패 | 시간 축이 깨진 행 |
| 이상치 카운트 | 규칙에 어긋나는 값의 수 |
| 코드북 미매칭 | 참조 테이블에서 찾지 못한 코드 |

실물 예시는 [`reports/dq_meta_sample.json`](./reports/dq_meta_sample.json)에 있습니다.

## 실패를 지우지 않았다

첫 실행은 파티션 제한과 날짜 파싱 문제로 중단됐습니다. 그 실행의 ID를 지우지 않고 리포트에 남겼습니다.

> "이전 실패(run_id=20251224_161451)는 파티션 제한/날짜 파싱 이슈로 중단되어 본 보고서에 포함하지 않음"

성공한 실행만 남기면 나중에 같은 문제를 다시 만납니다. 실패한 실행이 무엇 때문에 멈췄는지가 기록되어 있어야 재발을 막을 수 있습니다.

## 비용 문제를 원인까지 파고든 사례

프로젝트 중반에 S3 비용이 예상보다 크게 나왔습니다. 보통 떠올리는 대응은 스토리지를 줄이거나 버전관리를 끄는 것입니다.

청구 내역을 뜯어보니 **비용의 대부분이 스토리지가 아니라 요청 비용**이었습니다. 버전관리를 껐어도 문제는 그대로였을 겁니다.

원인을 찾기 위해 조회 이력을 뽑아 날짜별로 대조했습니다. 대시보드에서 발생한 쿼리가 전체 조회의 절반 이상을 차지했고, 읽기 요청 비용은 전처리 작업량과 강하게 같이 움직였습니다. 작은 파일이 많고 스캔 범위가 넓으면 쿼리 한 번이 수천 번의 요청을 만든다는 것이 확인됐습니다.

**배운 것** 청구서의 총액이 아니라 항목 구성을 먼저 봅니다. 그리고 눈에 보이는 대상(저장 용량)이 아니라 실제 원인(요청 패턴)을 고칩니다.

절감액은 말하지 않습니다. 원인을 찾은 시점과 과정 종료 시점이 가까워 개선 후 재측정을 하지 못했습니다.

## 선택과 포기의 이유

| 문제 | 선택 | 포기한 것과 이유 |
|---|---|---|
| 같은 값을 두 필드가 다른 이름으로 제공 | 한쪽이 비면 다른 쪽으로 채운 뒤 결측 행 제거 | 둘 중 하나를 정답으로 고정하는 안을 버렸습니다. 원천 스키마가 도중에 바뀐 것이라 어느 쪽도 항상 옳지 않았습니다 |
| 결측이 하이픈 문자로 표기됨 | null로 정규화 | 문자열 그대로 두는 안을 버렸습니다. 하이픈이 숫자 컬럼에 섞이면 이후 집계가 전부 문자열 연산이 됩니다 |
| 코드 컬럼이 숫자처럼 보임 | 문자열 유지 | 정수 변환을 버렸습니다. 선행 0이 사라지면 코드북 매칭이 조용히 실패합니다 |
| 이상치가 존재 | 세기만 하고 버리지 않음 | 규칙 기반 드롭을 버렸습니다. 기상 데이터의 극값은 오류일 수도 실제일 수도 있어 수집 단계가 판단할 자리가 아닙니다 |
| 대용량 전처리 비용 | Bronze에서 Silver 파티셔닝을 로컬에서 수행 | 전 구간 클라우드 처리를 버렸습니다. 교육 계정 예산 안에서 반복 재처리를 하려면 이 방법뿐이었습니다. 성능 최적화가 아니라 비용 회피 판단입니다 |
| 다른 구성원에게 인계 필요 | 로컬 결과를 정답 레퍼런스로 삼고 규칙을 문서로 전달 | 코드를 그대로 넘기는 안을 버렸습니다. 실행 환경이 달라 같은 규칙을 재현할 수 있는지가 더 중요했습니다 |

## 현재 한계

- **재현 범위가 제한적입니다.** 파서와 품질 불변식은 원본 데이터 없이 테스트로 검증됩니다. 실제 수집은 공공데이터포털 서비스키가 있어야 하고, 전체 백필과 클라우드 증분은 계정 종료로 불가능합니다
- **원본 작업 트리의 참조 일부가 이 저장소에 없습니다.** 명세 문서가 가리키는 EDA 산출물과 코드북 갱신 스크립트가 인계 패키지에 포함되지 않았습니다. 목록은 [LIMITS.md](./docs/LIMITS.md)에 있습니다
- **원천별 제공 시작일을 단정하지 않습니다.** 당시 기록마다 값이 달라 확정하려면 원천 manifest 재집계가 필요한데 근거 파일이 없습니다
- 농업기상 원천 4개 중 대시보드까지 완주한 것은 1개입니다. 나머지는 중간 계층에서 멈췄습니다
- 팀 자동화로 데이터 준비 시간이 줄었다는 회고가 있으나 팀 공동 성과이며 측정 방법이 남아 있지 않습니다
- 교육 과정 프로젝트입니다. 실사용자, 트래픽, 운영 기간이 없습니다

## 실행 방법

```bash
pip install -r requirements.txt

# 데이터 없이 지금 바로 되는 것
pytest                      # 파서 3종, 품질 불변식, 마스킹 검증

# 서비스키가 있을 때
cp .env.example .env        # AGRIWEATHER_SERVICE_KEY 입력
python -m src.kma_crop_detail.collect --start-date 2025-12-01 --end-date 2025-12-02 --limit-requests 5
python -m src.kma_crop_detail.parse   --input data/raw/KMA_CROP_DETAIL --output data/bronze
python -m src.common.silverize        --dataset KMA_CROP_DETAIL --input data/bronze --output data/silver
```

서비스키는 [공공데이터포털](https://www.data.go.kr)에서 발급합니다. `.env`는 추적되지 않습니다.
